## AITER/vLLM Source Notes

There is no usable AITER ROCm runtime environment on this machine, so AITER can only be used as source reference here. Do not treat any local AITER microbench as validated.

Source evidence:

- vLLM's Kimi-K2.5 AMD recipe uses `VLLM_ROCM_USE_AITER=1`, `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4`, `--tensor-parallel-size 8`, and `--block-size=1`.
- vLLM AITER MoE routes through `rocm_aiter_ops.fused_moe(...)`, not a generic PyTorch/tinygrad dequant+matmul path.
- AITER `fused_moe.py` has decode-specific logic:
  - `get_ksplit(...)` only enables split-K when `token * topk <= expert`, i.e. the batch=1/topk=8 Kimi shape is explicitly targeted.
  - `use_nt(...)` enables non-temporal load when `token * topk // expert < 64`, also true for batch=1.
  - tuned config lookup chooses `block_m`, `ksplit`, and exact kernel names.
- AITER Kimi FP4 tuned config has token=1 rows for `model_dim=7168`, `expert=384`, `topk=8`, `inter_dim=256/512`, around 22-25 us total on its recorded target. This is not directly comparable to our GGUF Q4_0 path, but it shows AITER has a special fixed-shape Kimi decode kernel family.
- vLLM QuickReduce supports ROCm all-reduce quantization regimes including INT4, but it is tied to vLLM's TP path and supported world sizes. This is separate from current tinygrad layer shard.

Interpretation:

- The reported vLLM/AITER speed should not be read as proof that tinygrad layer shard can scale. vLLM is using a different stack: AITER fused MoE, fixed-shape/tuned kernels, TP=8, block-size=1, and INT4 quick reduce.
- The source does support one actionable idea for tinygrad: reproduce AITER's single-GPU decode tricks first, especially selected/tuned MoE and split-K occupancy, before trying cross-GPU TP again.

## Q4 Expert Preshuffle Microbench

Script:

```sh
/tmp/b1/bench_q4_preshuffle.py
```

This tests a load-time preshuffle candidate for selected expert gate/up:

- current layout: separate `gate_w` and `up_w` Q4_0 raw buffers
- preshuffled layout: one interleaved `gate|up` Q4_0 buffer, so each selected expert row/block reads gate and up from adjacent memory

The benchmark pre-quantizes input to Q8_0 once and times only the selected Q4 x Q8 gate/up -> Q8 kernel. It does not include one-time load-time conversion cost.

8 expert slice:

```text
raw separate       kernel median 52.88 us, min 50.84 us
gate_up interlv    kernel median 46.16 us, min 44.08 us
```

384 expert address space with spread selection `sel=[0, 54, 108, 162, 216, 270, 324, 383]`:

```text
raw separate       kernel median 52.52 us, min 50.92 us
gate_up interlv    kernel median 46.28 us, min 44.64 us
```

Interpretation:

- Interleaving gate/up Q4 expert weights has a repeatable kernel-level gain of about 12-13% for the gate/up custom kernel.
- This is real but small in full decode terms. Current profile had gate/up custom at about 4.38 ms per steady graph, so this likely saves roughly 0.5-0.6 ms/token if integrated cleanly.
- Expected full decode impact is around 2%, not a path to 70 tok/s by itself.
- It is still a reasonable low-risk optimization because it is load-time layout only and does not introduce multi-GPU communication.

Integration attempt:

```sh
TMPDIR=/tmp/b1 TMP=/tmp/b1 TEMP=/tmp/b1 JITBEAM=2 CUSTOM_KIMI_MOE_Q8=1 CUSTOM_KIMI_SHARED_Q8=1 CUSTOM_KIMI_GATEUP_INTERLEAVE=1 PYTHONPATH=. \
python3 tinygrad/llm/cli.py \
  --model /raid/gguf/kimi/Kimi-K2.6-UD-Q4_K_XL-00001-of-00014.gguf \
  --shard 4 --benchmark 6
```

Two production wiring attempts failed:

```text
dummy replacement for gate/up weight: tried to allocate a 21.00 GB dummy parameter during JIT
keep original raw + attach interleaved raw: OOM while allocating a 5.91 GB interleaved buffer, used 188.21 GB on AMD
```

Conclusion: full-model preshuffle is not viable with the current loader/memory layout. It would need a loader that writes interleaved raw directly without ever keeping separate gate/up raw, which is too intrusive for an expected ~0.5 ms/token gain.

GGUF tensor-order check on the 14 split files:

```text
split.count = 14
block_count = 61
typ = 2 for ffn_{down,gate,up}_exps.weight
expert tensor order within most layers: down, gate, ..., up
split boundaries often separate gate and up, for example blk.5 gate is in split 00002 and blk.5 up is first in split 00003
```

Implication: a no-peak-memory preshuffle cannot be a local `_ggml_tensor` change. It would need `gguf_load` to keep pending gate buffers across tensor entries and sometimes across split files, allocate the final interleaved buffer first, copy gate/up directly into their interleaved positions, and avoid constructing normal raw/dequant gate/up tensors that keep the original raw buffers alive. This is possible but significantly more invasive than a kernel-only change.

Limited production attempt:

- Added a temporary `CUSTOM_KIMI_GATEUP_INTERLEAVE=1` implementation that only interleaved gate/up pairs appearing in the same GGUF split.
- Cross-split layers fell back to the original separate gate/up raw path.
- The loader used broadcast placeholders for gate/up weights and kept the interleaved raw on the placeholder attribute.

## Fixed-shape Q8_0 GEMV/Fusion Microbench

Script:

```sh
/tmp/b1/bench_q8_fixed_gemv.py
```

Shape tested first:

```text
shared expert gate/up: K=7168, N=2048
```

This compares current tinygrad Q8_0 lazy dequant/matmul expression against a fixed-shape custom kernel:

- generic path: two Q8_0 lazy dequant GEMV kernels, then `silu(gate) * up`
- custom path: quantize activation to Q8_0, then one fused Q8_0 x Q8_0 gate/up kernel that computes `silu(gate) * up`

Wall-time from the Python loop is polluted by schedule/expression construction, so the decision should use PROFILE GPU timestamps.

PROFILE GPU kernel times:

```text
generic gate GEMV     median 29.04 us
generic up GEMV       median 27.96 us
generic total         about 57.00 us

custom fused gate/up  median 17.28 us
activation q8         median 11.04 us
custom e2e total      about 28.32 us
```

Interpretation:

- This is a much stronger signal than Q4 preshuffle.
- Even charging a fresh activation quantization, fixed-shape fused Q8_0 shared-expert gate/up is about 2x faster at the GPU kernel level for this shape.
- In the real model, activation Q8 can potentially be shared with the selected expert custom Q4/Q8 gate/up in the same MoE block, which would make the custom gate/up path closer to 17 us than 28 us.
- Expected full decode impact is plausibly around 1.3-2.0 ms/token for 60 layers if integrated cleanly, depending on whether activation quantization is reused.
- This is now a higher-priority integration target than Q4 expert preshuffle.

## Next Plan

1. Do not run AITER microbench locally unless a real ROCm AITER environment is provided.
2. Keep shared expert down on the generic path unless a new kernel beats the real model, not just a standalone microbench.
3. Do not integrate full Q4 gate/up preshuffle unless the loader can avoid the separate raw + interleaved raw peak.
4. Do not integrate fixed-shape Q8 attention GEMV unless a whole-chain benchmark includes activation quantization and beats the real model.
5. Only after single-GPU kernels improve, revisit partial TP. Do not TP the whole block; only consider large isolated GEMV groups where copy/sync overhead is smaller than saved weight bandwidth.

Current working hypothesis:

- The 46 tok/s path is still mostly bandwidth/launch dominated, but the dominant bandwidth is no longer just selected Q4 expert weights.
- Kimi-specific fixed-shape Q8_0 GEMV/fusion is the next test with the best chance of a certain gain.
